# gnugo-wasm

GNU Go 3.8 compiled to WebAssembly via Emscripten for use in a browser or Node context.

## Download

Check the GitHub Releases section for the latest release. Each release contains a WASM binary, a JS file for loading it, optional TS type definitions for that JS, and the unmodified source as well as a copy of the GPL v3 license.


## Usage

A minimal example:
```js
import createGnuGo from "./gnugo.mjs"

// GTP input
const input = new TextEncoder().encode("boardsize 19\nplay B D4\ndragon_status D4\n")
let pos = 0

// stdout will get pushed onto here
const output = [] // number[]

// Make an instance and connect it to the input and the output.
const gnugo = await createGnuGo({
  stdin: () => {
    if (pos < input.length) return input[pos++]  // Feed bytes as long as they exist
    return null                                  // GNU Go reads as "no more input"
  },
  stdout: (byte) => {
    output.push(byte)
  },
})

// Start execution. Completes when it receives null over stdin
gnugo.callMain(["--mode", "gtp"])

// Decode output into text
const text = new TextDecoder().decode(new Uint8Array(output))
// "= \n\n= \n\n= alive\n\n"
```

`callMain` is synchronous, so all input that your `stdin` function reads must be ready before you call it. Each instance can only call `callMain` once, so use a new instance for each request.

While GTP replies go to `stdout`, GNU Go writes debug output, trace output, and error messages to `stderr`. If you do not give a `stderr` callback, `stderr` goes to `console.error`.

`gnugo.mjs` expects `gnugo.wasm` to exist in the same folder as it, but the `wasmBinary`, `locateFile`, and `instantiateWasm` options can change this. The TS type definitions are the best documentation here.

## Building

Requires Emscripten 6.0.12 (expects `emcc` to be in your `PATH`) and a native C compiler (`clang` by default, you can set the `NATIVE_CC` env var to specify an alternative).

```sh
./build.sh
```

The script is a two-stage build. First, a native build runs the GNU Go pattern generators, which write C source. Then `emcc` compiles the engine and that generated source. 

## Testing

`npm test` runs two separate tests:

1. `test/regress.sh` runs the built-in GNU Go regression tests. The build generates a second test-only JS file that operates as a proper Node script with filesystem access instead of a module, so it can be used as a test target. By default it runs `make check` (a relatively small batch of tests), but you can call `test/regress.sh test` to run the full standard suite. 

2. `node test/smoke.mts` runs the sample code given above in the "Usage" section and makes sure it runs and gives expected output. Since the regression test does not run on the exact codepath we ship (even if it's still a WASM binary generated by the same single build), this is to make sure our `gnugo.mjs` wrapper hasn't regressed.

This requires you to have installed dependencies (`npm install` or `npm ci`) and successfully built via `./build.sh`.


## Additions and Changes from Vanilla GNU Go

This project is largely a single build script that fetches the raw GNU Go 3.8 tarball and configures the build.

One exception is the patch files in the `patches/` directory (currently a single patch) which are applied as part of the build:

- 2026-10-14: `0001-gg_sort-empty-array-ub.patch`: `gg_sort` calculates a pointer before the start of an empty array. That is undefined behaviour, and clang at `-O1` and above miscompiles it. It now returns early in that situation.

Additionally, the TypeScript `.d.mts` type definition file is hand-written (i.e. generated by an LLM rather than emitted by `emcc`).
